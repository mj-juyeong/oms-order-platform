## 1. 우선순위 판단 기준

이번 피드백은 모두 중요하지만, 한 번에 다 구현하면 범위가 너무 커진다. 따라서 아래 기준으로 우선순위를 나눈다.

| 기준 | 설명 |
|---|---|
| 시연 신뢰도 | 다음 발표나 데모에서 바로 눈에 띄는 문제인가? |
| 운영 필수성 | 실제 운영자가 매일 쓰는 핵심 흐름인가? |
| 요구사항 충돌 여부 | 기존 OMS 원칙과 충돌하지 않고 바로 정리 가능한가? |
| 개발 의존성 | 다른 기능이 이 기능 위에 올라가는가? |
| 구현 난이도 | MVP 안에서 현실적으로 마무리 가능한가? |

## 2. 전체 우선순위 요약

| 우선순위 | 항목 | 판단 |
|---|---|---|
| P0 | 검색 결과 총 건수 정확화 | 화면 신뢰도에 직접 영향. 가장 먼저 고쳐야 함 |
| P0 | 필터 검색 버튼 방식 전환 | API 과호출과 건수 혼선을 줄이는 기본 구조 |
| P0 | 모바일 현재 상태 점검 | “모바일에서 많이 쓴다”는 피드백에 대한 즉시 대응 자료 필요 |
| P1 | 고객사 요청 관리 | 고객사 로그인의 핵심 가치. 주문 업로드 요청/마스터 추가 요청으로 정의 |
| P1 | 고객사 대시보드 | 고객사 로그인 후 볼 화면이 필요. 고객사 요청 관리와 연결됨 |
| P1 | 물류사 전체 API / API Key scope | 운영 연동 범위에 큰 영향. 정책 확정 후 구현 |
| P1 | 로딩/처리 진행 피드백 | 업로드/검증처럼 오래 걸리는 작업의 사용성 개선 |
| P1 | 디자인 색상 축소 | 시연 완성도와 운영툴 톤 개선 |
| P2 | API 호출 제한 | 중요하지만 정책 확인과 저장소 선택이 필요 |
| P2 | 브랜드별 상품코드 매핑 | 실제 코드 충돌 사례 확인 후 확장 |

## 3. 제가 보는 최우선 순서

개발 순서로 보면 아래가 가장 안전하다.

```text
1. 검색/필터/총 건수 정리
2. 모바일 화면 점검 및 깨짐 수정
3. 디자인 색상 정리
4. 로딩/처리 진행 피드백 개선
5. 고객사 요청 관리 설계 및 1차 구현
6. 고객사 대시보드 구현
7. 물류사 전체 API 및 API Key scope 확장
8. API 호출 제한
9. 브랜드별 상품코드 매핑
```

이유는 간단하다. 1~4번은 현재 화면의 완성도와 신뢰도를 올리는 작업이고, 기존 구조를 크게 흔들지 않는다. 5번부터는 신규 업무 모듈이므로 DB/API/권한/화면 설계가 필요하다.

## 4. P0 구현계획

## 4-1. 검색 결과 총 건수 정확화

### 문제

현재 일부 화면은 백엔드에서 받은 `totalElements`와 프론트에서 현재 페이지에만 적용한 필터 결과가 섞인다. 그래서 검색해도 `총 N건`이 그대로 보이거나, 실제 표시 행 수와 맞지 않는 문제가 생긴다.

### 구현 방향

검색 조건은 가능하면 백엔드 API로 보내고, 백엔드가 조건이 모두 적용된 결과의 `totalElements`를 반환한다.

### 대상 화면

| 화면 | 우선순위 | 이유 |
|---|---|---|
| 배치 목록 | 최우선 | 현재 keyword/dateRange/errorOnly 일부가 프론트 필터 |
| 주문 조회 | 최우선 | 운영 조회 핵심 화면 |
| Scan 조회 | 최우선 | storeName/productName 등 일부 프론트 필터 가능성 |
| PL 조회 | 높음 | 대량 데이터 조회 화면 |
| Label 조회 | 높음 | 대량 데이터 조회 화면 |
| 상품 마스터 | 높음 | 일부 현재 페이지 필터 가능성 |
| 배송지/차량 마스터 | 높음 | 검색 조건과 total 정합성 필요 |
| 이력/로그 | 중간 | 운영 추적 화면이나 시연 빈도는 낮을 수 있음 |

### Backend 작업

| 작업 | 설명 |
|---|---|
| 목록 API query parameter 확장 | keyword, date range, errorOnly, storeName, productName 등 누락 조건 추가 |
| Repository/Service 필터 정리 | 현재 `findAll().filter` 방식은 대량 데이터에서 위험하므로 DB query 전환 검토 |
| PageResponse 기준 통일 | 모든 목록 API가 조건 적용 후 `totalElements`, `totalPages` 반환 |
| 날짜 범위 지원 | 단일 날짜뿐 아니라 from/to 검색 지원 |

### Frontend 작업

| 작업 | 설명 |
|---|---|
| `totalElements` 의미 통일 | 화면의 `총 N건`은 백엔드 검색 결과 총 건수로만 사용 |
| 현재 페이지 필터 제거 | 프론트 필터가 꼭 필요하면 `현재 페이지 내 N건`으로 별도 표시 |
| 페이지 초기화 | 검색 조건 적용 시 page를 첫 페이지로 초기화 |
| 빈 상태 문구 정리 | “검색 결과 없음”과 “데이터 없음”을 구분 |

### 완료 기준

- 검색 조건 적용 후 `총 N건`이 실제 결과와 일치한다.
- 페이지 이동 시 같은 검색 조건이 유지된다.
- 현재 페이지에서만 필터링되어 total과 표가 어긋나는 화면이 없다.

## 4-2. 필터 검색 버튼 방식 전환

### 문제

현재는 필터 입력 중에도 API가 호출되는 화면이 많다. 사용자가 입력하는 중간값으로 검색이 실행되어 불필요한 호출이 발생하고, 화면이 자주 바뀐다.

### 구현 방향

필터 상태를 두 개로 나눈다.

```text
draftFilters: 사용자가 입력 중인 값
appliedFilters: 마지막으로 검색 버튼을 눌러 실제 적용된 값
```

### Frontend 패턴

```text
1. 사용자가 필터 입력
2. draftFilters만 변경
3. “검색” 버튼 클릭
4. appliedFilters = draftFilters
5. page = 0 또는 1
6. API 호출
```

### 공통 컴포넌트 개선

| 컴포넌트 | 개선 |
|---|---|
| `FilterBar` | `검색`, `초기화`, `상세 필터` 액션을 표준화 |
| `DateRangeQuickFilter` | 변경 즉시 검색하지 않고 draft만 변경 |
| 목록 페이지 | `useEffect` dependency를 `appliedFilters`, `page`, `reloadSeq` 중심으로 정리 |

### 완료 기준

- 필터 입력만으로 API가 호출되지 않는다.
- `검색` 버튼을 눌러야 결과가 바뀐다.
- 검색 전 변경된 조건이 있으면 “적용되지 않은 조건이 있습니다” 같은 표시를 할 수 있다.

## 5. P1 구현계획

## 5-1. 고객사 요청 관리

### 기능 정의

고객사가 OMS에서 직접 주문을 생성하거나 마스터를 수정하는 기능이 아니다. 고객사가 물류사에게 처리 요청을 등록하고, 물류사가 접수/처리/완료하는 기능이다.

요청 유형은 두 가지로 시작한다.

| 요청 유형 | 설명 |
|---|---|
| `ORDER_UPLOAD` | 고객사가 주문 업로드 처리를 요청 |
| `MASTER_DATA_ADD` | 고객사가 상품/배송지/차량/코드 매핑 등 마스터 데이터 추가를 요청 |

### 사용자 흐름

고객사:

```text
요청 등록
→ 첨부파일/메모 입력
→ 요청 제출
→ 처리 상태 확인
→ 물류사 보완 요청 시 답변
→ 완료 결과 확인
```

물류사:

```text
요청함 확인
→ 접수 / 반려 / 보완 요청
→ 담당자 처리
→ 주문 업로드 배치 또는 마스터 반영 이력 연결
→ 완료 처리
```

### Backend 작업

| 작업 | 설명 |
|---|---|
| 요청 테이블 추가 | `client_requests` |
| 첨부파일 테이블 추가 | `client_request_attachments` |
| 댓글/보완 요청 추가 | `client_request_comments` |
| 상태 이력 추가 | `client_request_status_logs` |
| 연결 정보 추가 | `upload_batch_id`, `master_upload_batch_id` 또는 별도 link table |
| 요청 API | 고객사 등록/조회, 물류사 목록/상세/상태 변경 |
| 권한 적용 | CLIENT는 자기 고객사 요청만, TENANT는 자기 tenant 요청 전체 |

### Frontend 작업

| 화면 | 설명 |
|---|---|
| 고객사 요청 등록 | 주문 업로드 요청/마스터 데이터 추가 요청 선택 |
| 고객사 요청 목록 | 내 요청 상태 확인 |
| 고객사 요청 상세 | 첨부파일, 댓글, 상태 이력 확인 |
| 물류사 요청함 | 전체 고객사 요청 목록 |
| 물류사 요청 상세 | 접수/반려/보완 요청/완료 처리 |

### 상태 후보

| 상태 | 의미 |
|---|---|
| `REQUESTED` | 고객사 요청 등록 |
| `REVIEWING` | 물류사 검토 중 |
| `ACCEPTED` | 물류사 접수 |
| `NEEDS_MORE_INFO` | 고객사 보완 필요 |
| `REJECTED` | 반려 |
| `IN_PROGRESS` | 처리 중 |
| `COMPLETED` | 처리 완료 |
| `LINKED_TO_BATCH` | 주문 업로드 배치와 연결 |
| `LINKED_TO_MASTER_UPLOAD` | 마스터 업로드 이력과 연결 |

### 먼저 확인할 것

- 주문 업로드 요청 첨부파일이 OIS 처리 전 파일인지, OIS 처리 결과 파일인지
- 마스터 추가 요청을 파일로 받을지, 화면 입력으로 받을지
- 완료 시 실제 배치/마스터 업로드 이력 연결을 필수로 할지

## 5-2. 고객사 대시보드

### 문제

현재 대시보드는 물류사 운영자 관점이다. 고객사 사용자가 로그인했을 때 “내가 요청한 것이 어떻게 처리되고 있는지”가 잘 보이지 않는다.

### 고객사 대시보드 1차 위젯

| 위젯 | 설명 |
|---|---|
| 내 요청 현황 | 주문 업로드 요청, 마스터 추가 요청 상태별 건수 |
| 보완 필요 요청 | 물류사가 추가 정보를 요청한 건 |
| 최근 완료 요청 | 처리 완료된 요청 |
| 납품/출고 예정 | 확정 배치 기준 오늘/내일 예정 데이터 |
| 오류/보류 알림 | 고객사와 관련된 검증 오류 또는 반려 사유 |

### 구현 방향

- `userScopeType === CLIENT`이면 고객사 대시보드를 보여준다.
- `TENANT`이면 기존 물류사 운영 대시보드를 보여준다.
- 같은 `/dashboard` 경로를 쓰되 scope에 따라 구성만 분기한다.

### 완료 기준

- 고객사 로그인 시 고객사 관점의 카드와 요청 목록이 보인다.
- 물류사 운영 지표가 고객사에게 과도하게 노출되지 않는다.

## 5-3. 물류사 전체 API 및 API Key scope 확장

### 문제

현재 외부 API는 고객사 단위 API Key만 허용하는 구조다. 물류사가 전체 고객사의 데이터를 통합 조회해야 한다면 이 구조가 부족하다.

### 정책 후보

| API Key 유형 | clientId | 접근 범위 |
|---|---:|---|
| 고객사 API Key | 있음 | 특정 고객사 데이터 |
| 물류사 API Key | 없음 | tenant 전체 고객사 데이터 |

### Backend 작업

| 작업 | 설명 |
|---|---|
| API Key scope 정책 정리 | `TENANT` / `CLIENT` 범위 명확화 |
| 외부 API 인증 수정 | `clientId == null` 금지 로직 완화 여부 검토 |
| query service 수정 | clientId optional 조회 지원 |
| 응답 필드 보강 | tenant-wide 응답에는 clientId/clientName 포함 |
| 감사 로그 수정 | clientId nullable 로그 가능 여부 검토 |

### Frontend 작업

| 화면 | 개선 |
|---|---|
| API Key 관리 | 고객사 Key / 물류사 Key 구분 |
| API 제공 현황 | 고객사별 보기 / 전체 보기 토글 |
| API 가이드 | scope별 호출 예시 분리 |

### 먼저 확인할 것

- 물류사 전체 API가 실제 운영 필수인지
- 전체 API 응답에서 고객사 데이터가 섞여도 되는지
- 외부 시스템이 고객사별로 API를 따로 호출할 수 없는지

## 5-4. 로딩/처리 진행 피드백

### 대상

3차:

- SSE 또는 WebSocket 검토

## 5-5. 디자인 색상 축소

### 목표

화면을 운영툴답게 차분하게 정리한다. 색상은 정보 구분용으로만 쓰고, 장식적 색 사용을 줄인다.

### 권장 색 체계

| 역할 | 색 |
|---|---|
| Primary | teal 또는 blue 중 하나 |
| Neutral | slate/gray |
| Risk | red/amber |

### 구현 작업

| 작업 | 설명 |
|---|---|
| Badge tone 정리 | 너무 많은 tone 제거 |
| MetricCard 색 정리 | 카드별 색을 줄이고 텍스트 중심으로 변경 |
| 버튼 색 통일 | primary/secondary/ghost 기준 유지 |
| 상태 색 최소화 | Error/Warning/Info는 텍스트와 아이콘 병행 |

## 6. P2 구현계획

## 6-1. API 호출 제한

### 왜 P2인가

중요하지만 “3건”의 기준이 아직 불명확하다. 초당 3건인지, 분당 3건인지, 동시 3건인지에 따라 구현이 달라진다.

### 구현 후보

| 방식 | 설명 |
|---|---|
| 메모리 기반 | 단일 서버 local 개발에는 쉬움 |
| DB 기반 | 구현은 가능하지만 호출마다 DB 부하 |
| Redis 기반 | 운영 rate limit에 적합 |

### 권장

운영을 생각하면 Redis 기반 token bucket 또는 sliding window가 적합하다. MVP에서는 정책만 정리하고, 필요하면 간단한 메모리 기반으로 시작할 수 있다.

## 6-2. 브랜드별 상품코드 매핑

### 왜 P2인가

현재 요구사항은 직접 매칭이 기본이다. 브랜드별 상품코드 충돌 사례가 확인되면 확장해야 한다.

### 확인 후 설계

| 확인 | 설명 |
|---|---|
| 프랜차이즈 의미 | 브랜드인지, 고객사인지, 별도 조직인지 |
| 코드 충돌 사례 | 같은 clientProductCode가 브랜드별로 다른 상품을 뜻하는지 |
| 관리 주체 | 고객사가 요청하고 물류사가 승인하는지 |

### 확장 후보

```text
tenant_id + client_id + brand_name + client_product_code
  -> ezadmin_code
```

## 7. 구현 단계별 로드맵

## Phase 1. 조회 신뢰도 개선

목표: 검색 결과와 총 건수가 맞는 화면을 만든다.

작업:

- 목록 화면별 검색 조건 현황 정리
- 백엔드 query parameter 확장
- 프론트 현재 페이지 필터 제거 또는 라벨 분리
- `검색` 버튼 방식 적용
- 페이지네이션 정합성 확인

완료 기준:

- 주요 목록 화면에서 검색 후 total이 정확하다.
- 입력 중 자동 검색이 발생하지 않는다.

## Phase 2. 시연/모바일 완성도 개선

목표: 다음 발표에서 눈에 보이는 완성도를 올린다.

작업:

- 모바일 스크린샷 생성
- 깨짐 화면 수정
- 색상 축소
- 로딩 단계 표시

완료 기준:

- 모바일 주요 화면 캡처가 있다.
- 색상 사용이 차분해진다.
- 업로드/검증 중 사용자가 현재 상태를 알 수 있다.

## Phase 3. 고객사 기능 1차 구현

목표: 고객사 로그인 후 할 수 있는 일을 만든다.

작업:

- 고객사 요청 DB/API 설계
- 주문 업로드 요청 등록
- 마스터 데이터 추가 요청 등록
- 고객사 요청 목록/상세
- 물류사 요청함/처리 화면
- 요청과 배치/마스터 업로드 이력 연결

완료 기준:

- 고객사가 요청을 등록할 수 있다.
- 물류사가 요청을 접수/반려/완료할 수 있다.
- 처리 결과가 고객사에게 보인다.

## Phase 4. 고객사 대시보드

목표: 고객사가 로그인했을 때 필요한 정보를 바로 본다.

작업:

- CLIENT scope 대시보드 분기
- 요청 상태 카드
- 보완 필요 요청
- 최근 처리 완료 요청
- 납품/출고 예정 요약

완료 기준:

- 고객사 대시보드가 물류사 대시보드와 다르게 보인다.
- 고객사에게 필요한 요청/처리 상태가 첫 화면에 보인다.

## Phase 5. API 운영 확장

목표: 물류사 전체 API와 호출 제한 정책을 정리한다.

작업:

- API Key scope 정책 확정
- tenant-wide API 지원
- API 제공 현황 전체 보기
- API rate limit 정책 설계

완료 기준:

- 고객사 API Key와 물류사 API Key의 차이가 명확하다.
- 물류사 전체 API 필요 여부와 구현 방향이 결정된다.

## 10. 결론

가장 먼저 해야 할 일은 신규 기능이 아니라 현재 화면의 신뢰도를 높이는 것이다. 검색 결과 총 건수와 검색 버튼 방식은 사용자가 바로 체감하는 문제이며, 이후 고객사 대시보드나 API 확장을 하더라도 계속 영향을 준다.

그다음은 고객사 요청 관리다. 고객사 로그인의 핵심 가치는 단순 조회가 아니라 물류사에게 주문 업로드와 마스터 데이터 추가를 요청하고 처리 상태를 확인하는 데 있다.

물류사 전체 API, API 호출 제한, 브랜드별 상품코드 매핑은 모두 중요하지만 운영 정책 확인이 먼저 필요하다. 따라서 P1/P2로 두고, 정책이 확정되는 순서대로 구현하는 것이 안전하다.
