## 1. 전체 요약

이번 피드백은 크게 네 영역으로 나뉜다.

| 영역 | 핵심 피드백 | 의미 |
|---|---|---|
| 검색/조회 UX | 총 건수 고정, 자동 검색 대신 버튼 검색 | 대량 데이터 화면에서 현재 조회 조건과 결과 건수가 정확히 맞아야 한다. |
| 권한/업무 흐름 | 고객사 로그인, 주문 업로드 요청, 마스터 데이터 추가 요청, 물류사 전체 API | 현재 OMS가 물류사 운영자 중심이므로 고객사 관점과 물류사 통합 관점이 보강되어야 한다. |
| 외부 API 운영 | API Key 적용 범위, 호출 제한 | 고객사별 API만으로 충분한지, 물류사 단위 API와 rate limit이 필요한지 점검해야 한다. |
| UI/디자인 | 모바일 대응, 색상 축소, 로딩 피드백 | 실제 사용 환경과 발표/시연 품질을 위해 화면 밀도와 피드백 방식을 정리해야 한다. |

## 2. 피드백별 상세 정리

## 2-1. 총 몇 건 표시와 프론트엔드 검색 로직 점검

### 받은 피드백

- 검색 또는 필터 조건을 변경해도 화면의 `총 몇 건` 값이 그대로 고정되어 보인다.
- 사용자는 검색 결과가 줄어들었다고 기대하는데, 총 건수가 그대로라서 필터가 적용되지 않은 것처럼 보인다.

### 현재 구현 관찰

현재 일부 화면은 백엔드에서 받은 `PageResponse.totalElements`와 프론트엔드에서 현재 페이지 데이터만 다시 필터링한 결과를 섞어 사용한다.

대표 사례:

| 화면 | 현재 동작 | 문제 |
|---|---|---|
| 배치 목록 | 백엔드에는 `status`, `page`, `size` 정도만 보내고, `keyword`, `dateRange`, `errorOnly`는 현재 페이지의 `items`에서 프론트 필터링한다. | `totalElements`는 백엔드 총 건수라서 프론트 필터 결과와 불일치한다. |
| Scan 조회 | `batchId`, 정확한 단일 배송일, `scanCenter`, `storeCode`, `productCode`, `barcode`는 백엔드에 보낸다. `storeName`, `productName`, 넓은 날짜 범위 등은 현재 로드된 페이지에서 프론트 필터링한다. | 총 건수는 백엔드 조건 기준이고, 화면 표는 프론트 추가 필터 기준이라 숫자가 어긋날 수 있다. |
| 주문 조회 | 대부분의 조건은 백엔드에 전달하지만, 화면에서 다시 현재 페이지 기준 그룹핑/요약을 수행한다. | 총 조회 건수와 현재 페이지 요약 건수가 다른 개념인데 UI에서 혼동될 수 있다. |
| 상품 마스터 | `storageTemperature` 같은 일부 조건을 현재 페이지에서만 필터링한다. | 전체 검색 결과 건수와 현재 페이지 필터 건수가 분리된다. |

### 개선 방향

검색/필터 조건은 가능한 한 백엔드 API로 전달하고, 백엔드는 조건이 모두 적용된 `totalElements`, `totalPages`, `items`를 반환해야 한다.

권장 원칙:

- `총 N건`은 백엔드에서 모든 검색 조건을 적용한 결과 건수로 표시한다.
- 프론트에서 현재 페이지 데이터만 다시 필터링하는 방식은 최소화한다.
- 프론트 전용 필터가 꼭 필요하면 `현재 페이지 내 N건`처럼 별도 라벨을 사용한다.
- 검색 조건 변경 즉시 자동 호출하지 않고, 사용자가 `검색` 버튼을 눌렀을 때만 API를 호출하는 구조로 바꾼다.
- 필터 입력 상태와 실제 적용된 검색 조건 상태를 분리한다.

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 배치, 주문, Scan, PL, Label, 마스터 화면의 `총 N건` 표시 기준 전수 점검 |
| P0 | 프론트 현재 페이지 필터링과 백엔드 검색 조건이 섞인 화면 목록화 |
| P0 | 검색 조건을 백엔드 query parameter로 보낼 수 있도록 API 확장 |
| P1 | 프론트 필터 상태를 `draftFilters`와 `appliedFilters`로 분리 |
| P1 | `검색` 버튼 클릭 시 page를 0/1로 초기화하고 API 호출 |
| P1 | `총 N건`, `현재 페이지 N건`, `선택 N건` 라벨을 구분 |

### 확인 필요

- 모든 검색 조건을 DB 검색으로 처리할지, 일부 UI 보조 필터는 현재 페이지 필터로 남길지 결정이 필요하다.
- 대량 데이터 검색 성능을 고려해 LIKE 검색 범위와 인덱스 정책을 함께 정해야 한다.

## 2-2. 고객사 로그인 시 물류사에게 주문 요청 필요

### 받은 피드백

- 고객사가 로그인했을 때 물류사에게 업무 요청을 보낼 수 있어야 한다.
- 요청 유형은 크게 `주문 업로드 요청`과 `마스터 데이터 추가 요청`이다.
- 고객사가 직접 OMS 운영 데이터를 확정하거나 원본 주문을 생성한다는 뜻이 아니라, 물류사에게 처리 요청을 등록하고 진행 상태를 확인하는 흐름이 필요하다는 의미다.

### 의미

현재 요구사항의 핵심은 OIS가 만든 엑셀을 물류사가 업로드하고, OMS가 저장/검증/조회/API/다운로드를 제공하는 구조다. 즉, OMS는 원본 주문 생성 시스템이 아니다.

이번 피드백은 고객사가 OMS에서 직접 주문 데이터를 생성한다는 뜻이 아니라, 고객사가 물류사에게 필요한 작업을 요청하는 포털성 기능이 필요하다는 뜻으로 정리한다.

요청은 최소 두 갈래다.

| 요청 유형 | 고객사 입장 | 물류사 입장 | OMS 연결 |
|---|---|---|---|
| 주문 업로드 요청 | 주문 파일 또는 주문 처리 요청 정보를 등록한다. | 요청 내용을 확인하고 OIS/OMS 업로드 처리 여부를 결정한다. | 처리 후 `upload_batches`와 연결될 수 있다. |
| 마스터 데이터 추가 요청 | 신규 상품, 신규 배송지/매장, 차량/배송 정보 추가를 요청한다. | 상품 마스터 또는 배송지/차량 마스터 반영 여부를 검토한다. | 승인 후 마스터 업로드/upsert 또는 직접 관리 화면과 연결될 수 있다. |

### 주문 업로드 요청

고객사가 주문 업로드 요청을 등록하면 물류사는 이를 검토하고 실제 업로드 작업을 수행한다. 이때 OMS는 요청 접수와 처리 상태를 관리하고, 실제 운영 데이터는 기존 원칙대로 OIS 엑셀 업로드 배치에서 생성된다.

예상 입력 항목:

| 항목 | 설명 |
|---|---|---|
| 요청 제목 | 고객사가 식별할 수 있는 요청명 |
| 요청 배송일/납기일 | 주문 처리 기준일 |
| 브랜드/프랜차이즈 | 해당되는 경우 선택 |
| 첨부파일 | 주문 파일, 요청서, 참고자료 |
| 요청 메모 | 특이사항, 긴급 여부, 요청 배경 |
| 희망 처리 기한 | 물류사가 언제까지 처리해야 하는지 |

처리 결과:

- 물류사가 요청을 접수하면 상태가 변경된다.
- 물류사가 실제 OIS 엑셀 업로드를 수행하면 요청과 `upload_batch_id`를 연결한다.
- 반려 시 반려 사유를 고객사가 확인할 수 있어야 한다.

### 마스터 데이터 추가 요청

고객사가 신규 상품, 신규 매장/배송지, 차량/배송 관련 데이터가 필요할 때 물류사에게 추가 요청을 등록한다.

요청 대상:

| 대상 | 예시 | 연결 마스터 |
|---|---|---|
| 상품 | 신규 상품코드, 상품명, 박스입수량, 보관온도, CBM | 상품 마스터 |
| 배송지/매장 | 신규 발주고코드, 거래처명, 주소, 권역 | 배송지/차량 마스터 |
| 배송/차량 정보 | 차수, 차량명, 담당기사, 배송일 | 배송지/차량 마스터 |
| 코드 매핑 | 고객사/브랜드별 상품코드 또는 매장코드 | 고객사/브랜드별 코드 매핑 후보 |

처리 결과:

- 물류사가 요청을 검토한다.
- 승인되면 마스터 업로드 또는 마스터 관리 기능으로 반영한다.
- 반영 후 고객사는 처리 완료 여부와 반영된 코드/마스터 항목을 확인한다.
- 반려되면 사유와 보완 요청을 확인한다.

### 권장 방향

`고객사 요청 관리` 모듈을 별도로 두고, 요청 유형을 `ORDER_UPLOAD`와 `MASTER_DATA_ADD`로 구분한다.

예상 상태:

- `REQUESTED`: 고객사 요청 등록
- `REVIEWING`: 물류사 검토 중
- `ACCEPTED`: 물류사 접수
- `NEEDS_MORE_INFO`: 고객사 보완 필요
- `REJECTED`: 반려
- `IN_PROGRESS`: 물류사 처리 중
- `COMPLETED`: 처리 완료
- `LINKED_TO_BATCH`: 주문 업로드 요청이 OMS 업로드 배치와 연결됨
- `LINKED_TO_MASTER_UPLOAD`: 마스터 추가 요청이 마스터 업로드 이력과 연결됨

예상 화면:

- 고객사: 요청 등록, 요청 목록, 요청 상세, 보완 응답, 처리 상태 확인
- 물류사: 고객사 요청함, 접수/반려/보완요청, 담당자 배정, 배치 연결, 마스터 반영 연결

예상 테이블:

| 테이블 후보 | 목적 |
|---|---|
| `client_requests` | 고객사 요청 공통 헤더 |
| `client_request_attachments` | 요청 첨부파일 |
| `client_request_comments` | 고객사/물류사 간 보완 메모 |
| `client_request_status_logs` | 상태 변경 이력 |
| `client_request_links` | 업로드 배치 또는 마스터 업로드 이력 연결 |

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 고객사 요청 유형을 `주문 업로드 요청`, `마스터 데이터 추가 요청`으로 확정 |
| P0 | 고객사가 요청 시 첨부해야 하는 파일/필수 입력값 정의 |
| P1 | 고객사 요청 등록/목록/상세 화면 설계 |
| P1 | 물류사 요청함, 접수/반려/보완요청/완료 처리 화면 설계 |
| P1 | 요청과 `upload_batches`, `master_upload_batches` 연결 방식 설계 |
| P1 | 요청 상태 이력과 댓글/보완 요청 구조 설계 |
| P2 | 요청 완료 알림, SLA, 담당자 배정 기능 검토 |

### 확인 필요

- 주문 업로드 요청의 첨부파일은 OIS 입력 전 원본 주문 파일인가, OIS가 처리한 결과 파일인가?
- 고객사가 마스터 데이터 추가 요청 시 어떤 양식을 사용해야 하는가?
- 마스터 추가 요청은 물류사 승인 후 파일 업로드로만 반영할지, 화면 직접 추가도 허용할지?
- 요청 처리 완료 시 고객사에게 어떤 알림이 필요한가?
- 요청과 실제 업로드 배치/마스터 업로드 이력을 반드시 연결해야 하는가?

## 2-3. 물류사 입장에서 API 사용 점검

### 받은 피드백

- 현재 외부 API는 특정 고객사의 데이터만 받을 수 있는 구조로 보인다.
- 물류사 입장에서는 여러 고객사의 전체 데이터를 받을 수 있는 API가 필요할 수 있다.
- API Key를 고객사뿐 아니라 물류사에게도 적용할지 점검해야 한다.

### 현재 구현 관찰

현재 외부 API 인증은 `X-Api-Key`를 사용한다. 다만 `ExternalApiKeyAuthService`에서 `apiKey.clientId == null`이면 금지하고 있다.

현재 정책:

- API Key는 DB상 `tenant_id`와 nullable `client_id`를 가질 수 있다.
- 하지만 외부 API에서는 `client_id`가 반드시 있어야 한다.
- `/external/v1/wos/scan-upload`, `/external/v1/pl/picking-list`는 인증된 고객사 `clientId` 기준으로만 데이터를 조회한다.
- 내부 API 제공 현황 `/api/v1/external-api/status`도 `clientId`를 필수 파라미터로 받고 있다.

즉, 스키마는 물류사 단위 API Key를 준비할 수 있지만, 현재 외부 API 구현은 고객사 단위 API만 허용한다.

### 개선 방향

물류사 단위 API Key를 허용할지 정책 결정이 필요하다. 허용한다면 다음 두 가지 조회 모드를 분리한다.

| 모드 | clientId | 설명 |
|---|---:|---|
| 고객사 단위 API | 필수 | 특정 고객사 데이터만 조회 |
| 물류사 단위 API | 없음 또는 선택 | 물류사 tenant 아래 여러 고객사 데이터를 통합 조회 |

물류사 단위 API를 제공할 경우 응답에는 반드시 `clientId`, `clientCode`, `clientName` 또는 동등한 고객사 식별 필드가 포함되어야 한다.

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 물류사 단위 외부 API가 실제 운영상 필요한지 확인 |
| P0 | 물류사 단위 API Key 허용 여부 결정 |
| P1 | API Key scope를 `TENANT` / `CLIENT` 또는 `clientId nullable` 정책으로 명확화 |
| P1 | 외부 API query에서 `clientId` optional 처리 |
| P1 | tenant-wide API 응답에 고객사 식별 필드 추가 |
| P1 | API 제공 현황 화면도 물류사 전체/고객사별 토글 지원 |
| P2 | 고객사별 접근 제한과 감사 로그를 강화 |

### 확인 필요

- 물류사 API 사용자는 내부 시스템인가, 외부 연동사인가?
- 전체 데이터 API에서 고객사별 데이터가 섞여도 되는가?
- 고객사별 API Key와 물류사 API Key의 권한/만료/발급 주체를 어떻게 구분할 것인가?

## 2-4. 고객사 입장 대시보드 필요

### 받은 피드백

- 고객사 입장에서 보고 싶은 데이터가 현재 대시보드에 없다.

### 의미

현재 대시보드는 물류 운영자 관점이다. 즉, 배치 오류, 검증 상태, 확정 대기, API 제공 가능 여부처럼 물류사가 처리해야 하는 업무를 중심으로 구성되어 있다.

고객사 사용자는 다른 정보를 보고 싶어 한다.

예상 고객사 관심사:

- 내가 요청한 주문/출고 요청 상태
- 오늘/내일 납품 예정 건수
- 확정된 출고 데이터
- 오류 또는 보류 사유
- 상품/매장/브랜드별 처리 현황
- 다운로드 가능한 라벨/출고 자료
- 물류사 처리 진행률

### 권장 방향

사용자 scope에 따라 대시보드 구성을 분리한다.

| 사용자 scope | 대시보드 중심 |
|---|---|
| SYSTEM | 전체 tenant 운영 현황, 장애/사용량 |
| TENANT | 고객사별 업로드/검증/확정/API/다운로드 운영 현황 |
| CLIENT | 내 고객사 주문 업로드 요청, 마스터 데이터 추가 요청, 출고/납품 예정, 처리 상태, 오류/보류 안내 |

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 고객사 사용자가 볼 수 있는 데이터 범위 확정 |
| P1 | 고객사 대시보드 KPI 정의 |
| P1 | 고객사 scope로 로그인했을 때 `/dashboard` 구성 분기 |
| P1 | 고객사 대시보드용 API 집계 설계 |
| P2 | 고객사 요청/문의/알림 위젯 추가 |

### 확인 필요

- 고객사에게 배치/검증 오류 상세를 어디까지 노출할 것인가?
- 고객사가 직접 다운로드할 수 있는 파일 범위는 무엇인가?
- 고객사 대시보드는 브랜드별, 매장별, 배송일별 중 어떤 축이 가장 중요한가?

## 2-5. 모바일틱하게 만들기 및 모바일 현재 화면 제시

### 받은 피드백

- 모바일에서도 사용이 많을 것으로 예상된다.
- 현재 모바일 환경에서 화면이 어떻게 보이는지 보여줄 필요가 있다.
- 화면을 모바일 친화적으로 만들어야 한다.

### 의미

OMS는 대량 테이블 중심 시스템이지만, 운영 현장에서는 태블릿/모바일로 상태 확인, 검증 결과 확인, 다운로드/요청 처리 같은 작업을 할 가능성이 있다.

모바일에서 특히 중요한 부분:

- 사이드바/상단 메뉴가 접히는지
- 필터가 너무 길지 않은지
- 표가 가로 스크롤로만 버티는지, 카드형 대체 뷰가 필요한지
- 주요 액션 버튼이 손가락 터치 크기를 만족하는지
- 모달/Drawer가 화면 밖으로 넘치지 않는지
- 배치 상세/검증 결과의 핵심 정보가 첫 화면에 보이는지

### 권장 방향

모바일 대응은 “모든 대량 테이블을 모바일에서 완벽히 편집”하는 목표보다, 주요 현장 확인 흐름을 빠르게 볼 수 있게 하는 것이 현실적이다.

- 390 x 844: 일반 모바일 세로
- 430 x 932: 큰 모바일 세로
- 768 x 1024: 태블릿 세로
- 1024 x 768: 태블릿 가로

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 현재 주요 화면의 모바일 스크린샷 캡처 |
| P0 | 모바일에서 깨지는 화면 목록화 |
| P1 | 목록형 화면은 모바일 카드 뷰 또는 요약 행 제공 |
| P1 | 필터 패널은 모바일에서 접힘/하단 시트 방식 검토 |
| P1 | 모달은 모바일에서 전체 화면 또는 92vh 패널로 통일 |
| P2 | 모바일 전용 하단 주요 액션 영역 검토 |

### 확인 필요

- 모바일에서 실제로 수행할 업무가 조회 중심인지, 업로드/확정/다운로드까지 포함하는지?
- 현장 사용자는 물류사 운영자인지, 고객사 사용자인지?

## 2-6. 디자인 색 줄이기: 3개 색 중심

### 받은 피드백

- 현재 디자인이 다소 알록달록해 보인다.
- 색상을 3개 정도로 줄였으면 한다.

### 의미

현재 화면은 상태별 Badge, MetricCard, Alert 등에서 teal, blue, green, amber, red, slate 등 여러 색을 동시에 사용한다. 운영툴에서는 색이 많으면 정보 강조가 분산되고, 무엇이 중요한 상태인지 한눈에 들어오지 않을 수 있다.

### 권장 색상 원칙

업무 시스템에서는 3개의 기본 색 축으로 정리하는 것이 좋다.

| 역할 | 권장 색 | 사용처 |
|---|---|---|
| Primary | Teal 또는 Blue 중 1개 | 주요 버튼, 링크, 활성 메뉴, 핵심 수치 |
| Neutral | Slate/Gray | 배경, 테이블, 일반 텍스트, 비활성 상태 |
| Risk | Red/Amber 계열 | Error, Warning, 위험 액션 |

단, Error와 Warning은 업무상 구분이 필요하므로 완전히 같은 색으로 합치면 안 된다. “3개 색” 원칙을 적용하더라도 위험 계열 안에서 Red/Error, Amber/Warning 정도는 텍스트와 아이콘으로 구분하는 것이 필요하다.

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 현재 사용 색상 토큰 전수 점검 |
| P1 | Primary 색 1개 선택: teal 또는 blue |
| P1 | Badge tone과 MetricCard tone 정리 |
| P1 | 화면별 decorative 색상 제거 |
| P1 | Error/Warning/Info는 색보다 라벨/아이콘 중심으로 구분 |
| P2 | 디자인 시스템 문서에 색상 사용 규칙 추가 |

### 확인 필요

- 브랜드 컬러가 있는지?
- 발표/시연용 톤과 실제 운영용 톤을 동일하게 갈지?

## 2-7. 필터 검색을 버튼으로 찾기

### 받은 피드백

- 현재는 입력할 때마다 검색이 자동으로 수행된다.
- 다소 불필요하므로 `검색` 버튼을 클릭했을 때 검색되게 바꾸는 것이 좋다.
- 현재 검색 로직이 어떻게 되고 있는지 설명이 필요하다.
- 가능하면 검색 결과 건수는 백엔드에서 반환하게 하는 것이 좋다.

### 현재 구현 관찰

현재 많은 화면은 React `useEffect` dependency에 필터 값을 넣어두고, 필터 입력이 변경되면 자동으로 API를 다시 호출한다.

예:

- 주문 조회: `filters` 전체가 변경되면 `omsApi.orders.list(...)` 자동 호출
- Scan 조회: `filters.batchId`, `filters.barcode`, `filters.deliveryDateRange`, `filters.productCode`, `filters.scanCenter`, `filters.storeCode` 등이 바뀌면 자동 호출
- 배치 목록: `status`는 백엔드 재조회, 나머지 필터는 현재 페이지 프론트 필터링

공통 `FilterBar` 컴포넌트는 `onSubmit`을 받을 수 있지만, 실제 페이지 중 상당수는 버튼 검색 구조로 통일되어 있지 않다.

### 개선 방향

필터 입력값과 실제 조회 조건을 분리한다.

```text
draftFilters: 사용자가 입력 중인 값
appliedFilters: 마지막으로 검색 버튼을 눌러 API에 적용된 값
```

흐름:

1. 사용자가 필터 입력
2. 화면은 아직 API 호출하지 않음
3. 사용자가 `검색` 버튼 클릭
4. page를 첫 페이지로 초기화
5. `appliedFilters = draftFilters`
6. 백엔드 API 호출
7. 백엔드가 `items`, `totalElements`, `totalPages` 반환

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 주요 조회 화면의 자동 검색 동작 목록화 |
| P0 | `FilterBar`를 `검색`, `초기화`, `상세 필터` 구조로 통일 |
| P1 | `draftFilters` / `appliedFilters` 패턴 도입 |
| P1 | 검색 버튼 클릭 시에만 API 호출 |
| P1 | 검색 조건 변경 후 미적용 상태 표시: “변경된 조건이 있습니다” |
| P1 | 백엔드 목록 API가 모든 검색 조건과 총 건수를 처리하도록 확장 |

## 2-8. API 호출 제한 고려

### 받은 피드백

- 보통 API 호출을 3건으로 제한하는 경우가 있으므로 이 부분을 고려해야 한다.

### 의미

외부 API는 WOS/PL 같은 외부 시스템이 호출한다. 호출 제한이 없으면 실수나 장애로 과도한 호출이 발생할 수 있고, 운영 DB에 부하가 생길 수 있다.

현재 구현에는 명시적인 rate limit 또는 throttle 로직이 없다.

### 정책 후보

| 정책 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 초당 3건 | API Key별 초당 3회 호출 | 단순하고 일반적 | 대량 연동 시 너무 낮을 수 있음 |
| 분당 180건 | 초당 3건과 유사하되 burst 허용 | 실무 연동에 유연 | 구현이 조금 더 복잡 |
| endpoint별 제한 | WOS/PL API별 제한 | 부하 제어 세밀 | 운영 정책 관리 필요 |
| tenant/client별 제한 | API Key가 아니라 고객사/물류사 기준 제한 | 키를 여러 개 발급해 우회하는 문제 방지 | 집계 저장소 필요 |

### 권장 방향

1차는 API Key별 rate limit을 적용하고, 응답 헤더로 잔여 호출 정보를 제공하는 방식을 검토한다.

예상 응답:

- 정상: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
- 제한 초과: HTTP `429 Too Many Requests`

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | “3건”의 기준이 초당/분당/동시 호출인지 확인 |
| P1 | API Key별 rate limit 정책 설계 |
| P1 | 429 오류 응답 포맷 정의 |
| P1 | API 호출 로그에 제한 초과도 기록 |
| P2 | Redis 같은 외부 저장소가 필요한지 검토 |

### 확인 필요

- 3건 제한은 초당 3건인가, 동시 처리 3건인가, 하루 3건인가?
- 외부 연동사가 batch 단위로 대량 페이지 호출을 해야 하는가?
- 제한 초과 시 재시도 정책을 어떻게 안내할 것인가?

## 2-9. 프랜차이즈별/브랜드별 상품코드 매핑

### 받은 피드백

- 프랜차이즈별 상품코드 매핑이 필요할 수 있다.
- 여기서 프랜차이즈는 브랜드별을 의미하는 것 같다.
- 브랜드별 상품코드가 매핑되고 있는지, 물류사가 그 매핑을 볼 수 있는지, 실제로 필요한지 점검해야 한다.

### 현재 요구사항 기준

현재 1차 MVP 기준은 고객사 코드 매핑 없이 직접 매칭이다.

- 운영 데이터 `product_code` -> 상품 마스터 `ezadmin_code`
- 운영 데이터 `store_code` 또는 `order_business_site_code` -> 배송지/차량 마스터 `baljugo_code`

다만 확장 후보로 `client_product_code_mappings`, `client_store_code_mappings`가 이미 언급되어 있고, 현재 코드에도 고객사별 코드 매핑 엔티티가 존재한다.

### 피드백의 추가 의미

고객사 단위 매핑만으로 부족하고, 같은 고객사 안에서도 브랜드/프랜차이즈별 상품코드가 다를 수 있다는 의미일 수 있다.

예:

```text
tenant_id + client_id + brand_code/name + client_product_code
  -> ezadmin_code
```

또는:

```text
tenant_id + franchise_id + client_product_code
  -> ezadmin_code
```

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | “프랜차이즈”가 실제로 `brandName`인지 별도 법인/가맹본부인지 확인 |
| P0 | 현재 엑셀의 브랜드 컬럼과 상품코드 관계 분석 |
| P1 | 기존 `client_product_code_mappings`로 충분한지 검토 |
| P1 | 브랜드별 매핑 테이블 필요 여부 검토 |
| P1 | 물류사가 매핑을 조회/업로드/수정할 화면 필요 여부 정의 |
| P2 | 검증 엔진에서 브랜드별 매핑을 적용할 우선순위 설계 |

### 확인 필요

- 브랜드별 상품코드가 실제로 중복/충돌하는 사례가 있는가?
- 브랜드명은 입력 엑셀에서 안정적으로 들어오는가?
- 브랜드별 매핑은 고객사가 관리하는가, 물류사가 관리하는가?

## 2-10. 로딩 시 실시간 처리 피드백

### 받은 피드백

- 로딩 중에 데이터를 얼마나 다운로드하거나 처리하고 있는지 실시간 피드백이 있으면 좋겠다.

### 의미

파일 업로드, 엑셀 파싱, 검증, 다운로드, 대량 조회는 시간이 걸릴 수 있다. 현재 단순 로딩 문구만 있으면 사용자는 멈춘 것인지 처리 중인지 알기 어렵다.

### 적용 대상

| 작업 | 필요한 피드백 |
|---|---|
| OIS 엑셀 업로드 | 업로드 진행률, 파일 전송 완료, 파싱 중, 저장 중 |
| 엑셀 파싱 | 시트별 처리 상태, 처리 행 수 |
| 검증 | 전체 행 중 검증 완료 행 수, Error/Warning 발생 수 |
| 마스터 업로드 | 전체 row, inserted/updated/unchanged/failed 진행 |
| 라벨 다운로드 | 파일 생성 중, 다운로드 준비 완료 |
| 대량 API 조회 | 현재 페이지 로딩, 전체 건수, 응답 시간 |

### 구현 방식 후보

| 방식 | 설명 | 적합한 작업 |
|---|---|---|
| 단순 단계 표시 | `업로드 중 -> 파싱 중 -> 저장 중 -> 완료` | MVP 빠른 적용 |
| polling | 배치 처리 상태 API를 주기적으로 조회 | 검증/파싱/다운로드 |
| Server-Sent Events | 서버가 진행률 이벤트를 push | 장시간 처리 |
| WebSocket | 양방향 실시간 상태 | 고도화 |
| XMLHttpRequest upload progress | 파일 전송 byte 진행률 | 업로드 |

### 권장 방향

1차는 단계형 진행 상태와 polling을 우선 적용한다. 실제 row 단위 진행률은 백엔드 작업 구조가 chunk/persist progress를 지원해야 하므로 후속 고도화로 둔다.

### 후속 작업

| 우선순위 | 작업 |
|---|---|
| P0 | 업로드/검증/다운로드별 현재 로딩 UX 점검 |
| P1 | 업로드 단계 상태 표시 추가 |
| P1 | 배치 상세에서 처리 단계 timeline 강화 |
| P1 | 검증 실행 후 polling으로 상태 갱신 |
| P2 | row 처리 진행률 저장 컬럼 또는 progress endpoint 설계 |
| P2 | SSE/WebSocket 필요성 검토 |

## 3. 백엔드/API 설계에 반영할 항목

| 항목 | 현재 | 개선 방향 |
|---|---|---|
| 목록 검색 총 건수 | 일부 화면에서 프론트 필터와 백엔드 total 혼재 | 모든 검색 조건을 백엔드에서 처리하고 `PageResponse.totalElements` 반환 |
| 외부 API 고객사 범위 | 고객사 API Key만 허용 | 물류사 tenant-wide API Key 허용 여부 검토 |
| API 제공 현황 | `clientId` 필수 | 물류사 전체 보기 또는 client optional 조회 검토 |
| API 호출 제한 | 없음 | API Key별 rate limit 검토 |
| 고객사 대시보드 | 물류사 운영 지표 중심 | CLIENT scope 전용 집계 API 필요 |
| 고객사 요청 | 없음 | 주문 업로드 요청과 마스터 데이터 추가 요청을 접수/처리하는 워크플로우 필요 |
| 브랜드별 코드 매핑 | 고객사별 코드 매핑 후보 있음 | 브랜드/프랜차이즈 축 추가 필요 여부 검토 |
| 진행률 | 단순 로딩 중심 | 단계/진행률 상태 API 또는 polling 필요 |

## 5. 우선순위 제안

### P0: 다음 시연 전 반드시 점검

- 검색 시 `총 N건`이 실제 검색 결과와 맞는지 점검
- 자동 검색을 버튼 검색으로 바꿀 대상 화면 목록화
- 현재 모바일 화면 스크린샷 캡처
- 외부 API가 고객사 단위만 가능한 현재 정책 설명 준비
- 고객사 대시보드/고객사 요청은 “신규 요구사항 후보”로 범위 정의
- 고객사 요청 유형을 `주문 업로드 요청`, `마스터 데이터 추가 요청`으로 분리해 설명 준비

### P1: MVP 반영 후보

- 주요 목록 API 검색 조건 확장
- `draftFilters` / `appliedFilters` 패턴 적용
- 물류사 단위 API Key와 tenant-wide 외부 API 설계
- 고객사 대시보드 1차 위젯 설계
- 업로드/검증 진행 상태 UI 개선
- 색상 체계 정리

### P2: 고도화 후보

- API rate limit 운영 저장소 도입
- 브랜드별 상품코드 매핑 관리 화면
- SSE/WebSocket 기반 실시간 진행률
- 모바일 전용 카드/하단 액션 UX

## 7. 결론

이번 피드백은 단순 UI 수정뿐 아니라 사용자 역할 확장, API 제공 범위 확장, 검색/페이징 정확성 개선을 요구한다.

가장 먼저 처리할 것은 검색 결과 총 건수와 검색 버튼 방식이다. 이 부분은 현재 화면 신뢰도에 직접 영향을 준다. 그다음 고객사 로그인 이후의 업무 가치, 물류사 전체 API, 고객사 대시보드를 별도 요구사항으로 확정해야 한다.

특히 고객사 요청 기능은 `주문 업로드 요청`과 `마스터 데이터 추가 요청`으로 정의한다. OMS가 원본 주문을 직접 생성하는 방향이 아니라, 고객사가 물류사에게 필요한 작업을 요청하고 물류사가 이를 접수/처리한 뒤 업로드 배치 또는 마스터 반영 이력과 연결하는 흐름으로 설계하는 것이 안전하다.
